# CeyPoS MCP Data Plane

## 1. Shop database lifecycle
- `workflow.md` and `server/src/routes/shop.js` enforce a single SQLite file per shop. During onboarding the Shop Wizard posts to `/api/shop/setup`; the backend creates `<sanitized-email>_idXXXXXXXXXXXX.db` inside `database/` using `createShopDb` in `server/src/utils/db.js`.
- A shop is considered ready only after Clerk confirms both the account and the matching `.db` file exist. Login flows must call `/api/shop/:shopId/exists` and deny dashboard access if the file is missing; **never** create a replacement file on login.
- `dbPathForShop` and `dbExists` centralise filename resolution. They normalise `shopId`, block path traversal, prefer an existing file, and only create a new one when explicitly asked during onboarding.

## 2. Backend change-bus architecture
- Mutations enter through REST (`inventory`, `sales`, `payment-methods`, etc.) or Socket.IO (`inventory:upsert`). Service layer helpers (`server/src/services/*.js`) write to SQLite via `better-sqlite3` transactions.
- Every write publishes a structured change on the in-process bus (`server/src/realtime/change-bus.js`) with `{changeId,timestamp,shopId,entity,action,payload,actor}`. Inventory upserts, sale completions, customer enrichments, daily sales rollups, and payment-method toggles all emit changes.
- `server/src/ws-server.js` subscribes to the bus, namespaces events by `shop_<id>`, and broadcasts them over Socket.IO. On connect it emits an `initialState` snapshot generated by `server/src/services/shop-snapshot.js`.
- This keeps all browser sessions, MCP clients, and future automation aligned without local caches drifting.

## 3. Frontend realtime cache
- The browser client (`src/lib/db.ts`) calls `db.connectWebSocket(shopId)` during `AppProvider` boot. It fetches `/api/shop/:shopId/snapshot`, hydrates in-memory maps, and attaches to the change stream.
- A per-entity monotonic guard (`lastAppliedChanges`) rejects stale events. Helpers like `db.products.getByShopId`, `db.sales.getByShopId`, and `db.paymentMethods.setEnabled` reuse the live cache instead of hitting REST repeatedly.
- Feature modules (analytics, dashboard, POS, etc.) listen to typed events (`inventoryUpdated`, `salesUpdated`, `saleCreated`, `paymentMethodsUpdated`) to stay reactive.

## 4. MCP/AI access path
- `/api/analytics/chat` (see `server/main-server.js`) proxies user questions to `processUserQuestion` in `mcp-server/mcp.js`.
- The MCP runtime wraps OpenAI with tool-calling. Tools such as `query_inventory`, `query_sales`, `query_customers`, `get_schema`, and `get_sample_data` are declared in `mcp-server/index.ts`. Each tool ultimately delegates to `queryDatabase`/`getSchema`/`getSampleData` in `mcp-server/database.ts`.
- Those helpers reuse `dbPathForShop` from the backend util module to locate the correct file and execute read-only queries (`sqlite3`/`better-sqlite3`). They intentionally open databases in `OPEN_READONLY` mode so the AI cannot mutate data outside the change bus.
- **Current gap:** the MCP server reads the file directly and does not subscribe to the change bus, so it only sees persisted state. That is acceptable for analytics queries but future real-time agents should mirror the bus to avoid polling.

## 5. Why the AI currently says “no data available”
- The analytics chat sidebar (`src/components/modules/analytics/ChatSidebar.tsx`) posts `{ shopId: '1755542590' }` to `/api/analytics/chat`. That placeholder does not match the real database filename (e.g. `ceypos@gmail.com_id13245`).
- `processUserQuestion` calls `db.dbExists(shopId)` inside `executeTool`. Because the shop ID is wrong, the check returns `false`, the tool responds with `Shop database not found`, and the LLM translates that into the user-facing apology.
- Fixes required:
	1. Read `currentShop` from `AppContext` and pass the actual `shopId` (and ideally the resolved `dbFileName`) to the chat request.
	2. Expose Clerk-validated shop metadata to the analytics module so every session shares the same identifier.
	3. Optionally fall back to listing known databases when a request arrives with an invalid ID, so operators can diagnose configuration mistakes faster.

## 6. Schema surface exposed to the AI
- `server/src/utils/db.js` initialises the following tables per shop: `shop_meta`, `shop_operating_hours`, `shop_payment_methods`, `inventory`, `customers`, `transactions`, `transaction_items`, `daily_sales`, and `inventory_forecast`.
- The MCP tools surface both a `get_schema` command (reads `sqlite_master`) and `get_sample_data` (defaults to 5 rows) so the AI can introspect column names before crafting analytics queries.
- All analytics visualisations (`ChatVisualization.tsx`) expect simple `{ name, value }` series. When returning chart data from the AI, keep the payload lean to avoid overfetching.
